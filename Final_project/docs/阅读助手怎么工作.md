# 阅读助手是怎么工作的

第 4 组，Track 5。这是给 Sprint 2 演示用的说明，尽量写得直白。它讲三件事：网站后面是什么、读者提一个问题之后发生什么、这一版用的是哪些线上模型。

## 这个产品是什么

CheeseO 是一个编程课博客。大部分课文是 Git 系列或 Docker 系列。

登录之后，读者可以在某一篇课文上提问，也可以打开完整聊天。助手只根据这个网站上的课文来回答，也可以建议接下来读哪一篇。如果读者想收藏一篇，或者发一条评论，助手只是先准备好这一步。读者按下确认（Confirm）之前，什么都不会保存。

没登录的人可以读课文，但看不到助手。

## 这个 agent 是什么

这里的 agent 不是一个什么都能聊的聊天机器人。它是这个博客的阅读助手。它只根据站内课文回答，也能帮读者做几件和阅读有关的事。站里没有这个话题时，第一句会说找不到，不会用自己的常识编一段。在完整聊天里，它接着直接给出博客外面的公开说明，并标明不是本站课文。说明后面有来源图标，点一下就打开那个网页。这些链接不放进 SOURCES。回答也会用到这个人已经读过的课文。

它每次回答都分三步，顺序是固定的：

1. 规则先看这句话想干什么，决定要叫哪些工具。这一步不是模型。
2. 工具去取事实：搜课文、看这个人读过什么、取出阅读路线，或者先准备好一项改动。
3. 线上模型只根据工具拿回来的结果写回复。结果是空的，它就说博客里没有这个话题。

所以它和普通搜索框不一样。搜索框只返回几条链接。这个 agent 会先选工具，再让模型把结果说成一句回答，并且在回答下面留下用过的课文链接。每次回复都会记下跑过哪些工具，方便我们回头看它为什么这样答。

改网站内容的动作更严。加入阅读清单、从清单移除、发评论，都只是先放在一张卡片上。读者按下确认才会真正保存。

学习面板不是这次提问里的 agent。面板上的难度和概念是事先算好、存在文件里的。打开页面时不会再叫一次模型。

## 它能做的事

- 解释或概括一篇课文。问题如果是从这篇页面发出的，它只在这一篇里找。
- 在整个博客里找一个话题，比如 Git 或 Docker，并说明哪几篇在讲这件事。
- 根据这个人最近打开过的课文，建议接下来读什么。推荐是按相同标签找的，不是模型随便点一篇。
- 说出这个人最近读过什么，方便接着读。
- 给出一条事先写好的阅读路线。现有路线包括 Git 入门、Git 分支、Docker、Python 基础、Python 网页开发，以及机器学习入门。
- 查看自己的阅读清单。
- 准备三项动作：把课文加进清单、从清单移除、写一条评论。这三项都要等确认。
- 在完整聊天里，站内没有课文时，直接附上博客外面的公开说明，并标明不是本站课文。来源不限维基百科，后面的图标可以打开原网页。

## 它不会做的事

- 不把不存在的课文说成站上有。Helm 那一句就是例子。第一句会说博客里没有这篇文章，不会说“那篇文章是这样讲的”。
- 不会把外面的说明放进 SOURCES，也不会把它叫成 CheeseO 的课文。来源图标只负责打开原网页。
- 不把付费课文的正文抄出来。没解锁的人只能看到一句付费提示。
- 不提供公司收入、密码或密钥。这类问题有一句固定拒绝，不会送给模型。
- 不在读者确认之前改清单或发评论。文章编号不存在时，也不会准备这一步。
- 找不到时，不会改口推荐站内另一篇课文来代替。
- 在某一篇课文的问答里，问的是别的主题时，不会拿当前打开的这篇来总结。回复会说明这个问答只覆盖这一篇，并指向完整聊天。

## 网站后面是什么

网站用 Django 搭的。Django 是一个 Python 框架，页面、登录和助手都由它来跑。课文本身放在 Wagtail 里。Wagtail 是编辑工具：我们在那里写课文，然后点发布。

代码分成几块：

- 博客负责课文、评论，以及这篇是免费还是付费。
- 助手负责聊天、搜索、学习面板和确认按钮。
- 账户负责登录、读者资料，以及这个人打开过哪些课文。登录用邮箱和密码。
- 会员和积分决定谁能打开付费课文。
- 首页是网站上其余的公开页面。

读者发出问题后，只有助手那个框会更新，整页不会重新加载。

课文、用户、聊天和搜索用的内容都存在 PostgreSQL 里。组里共用的数据库在 Supabase。共用网站上的图片也存在 Supabase。我们没有为搜索再单独装一个数据库。

## 读者看到什么

屏幕比较宽时，助手在课文右边的一栏里。手机上，读者从“问 AI”（Ask AI）打开它。完整聊天是另一个页面，地址是 `/agent/`。

右边这一栏做两件事。学习面板显示这篇有多难、里面有哪些概念，以及前后课文的链接。聊天框是读者打字提问的地方。

## 提问之后发生什么

每个问题都走同样的步骤。模型只在最后写回复。它自己不会去搜博客。

1. 如果问题是从某篇课文页面发出的，助手就只看这一篇。“Summarize this article” 总结的是这一篇。如果问题点名了别的主题，比如当前打开的是另一篇文章，却问 Helm，它不会拿当前这一页来总结。回复会说这个问答只覆盖打开的这篇，并指向 `/agent/`。这篇不存在，它会直接说，然后停下来。

2. 一组简单规则先读这个问题，判断它是哪一种请求。这不是模型。规则能认出来的包括：“这是什么意思”“接下来该读什么”“我已经读过什么”“把这篇加到我的清单”“发一条评论”。

3. 然后助手去搜索。
   - 关键词搜索：在标题和正文里找同样的词。
   - 段落搜索：课文被切成很多小段，在这些小段里找。
   - 按意思搜索：把问题变成一串数字，再和每一小段已经存好的数字比较。两串数字越接近，意思越接近。比较是在我们自己的代码里做的。这些数字就存在 PostgreSQL 里，跟小段放在一起。
   - 其他查询会看这个人打开过什么、阅读清单里有什么，以及事先准备好的阅读路线。
   - 在课文页面上，搜索只在这一篇里进行。在完整聊天里，搜索可以看整个博客。

4. 付费正文在给模型看之前会被拿掉。如果这个读者还没解锁这篇课文，付费段落会换成一句“这是付费内容”。模型被要求不要把藏起来的正文抄出来。

5. 有些问题根本不会送到模型。回复是写死的一句话。
   - 问公司收入、密码或密钥，直接拒绝。
   - “把整篇付费课文原文贴出来”，直接拒绝。回复会说这篇是付费的，只能给一个简短预览。
   - “把文章编号 999999 加进清单”，如果这个编号不是真课文，什么都不会准备。回复会说这篇文章不存在。

6. 收藏和发评论要等确认。“加到阅读清单”“从清单移除”“发评论”都只是先准备一张卡片。读者按下确认，改动才会保存。按取消（Cancel）就是丢掉。

7. 完整聊天里什么课文都没找到时，第一句仍然是写好的：“I cannot find any article about that topic in the blog corpus.” 然后直接查公开网页，不再等按钮。先从网页搜索结果里取最多四条，标题、摘要和网址都留下。维基百科或搜索引擎自己的短说明如果还没出现，会补进来。模型只能把这些摘录改写成两三句。回复标上 **Outside the blog**（不是本站课文）。回答下面有来源图标，点一下打开原网页。这些网址不进 SOURCES。一个结果都没有时，就说外面没有找到可用的公开说明，模型不会自己编。

8. 回答会带上这个人已经打开过的课文。文章页上的前置知识也会对照这份阅读记录：读过的算已读。评测结果里，如果这道题对着某一篇文章，会记下它的相关课文和前置知识；如果用了站外页面，也会记下那些链接。这一项是记录，不改变原来的对错。

9. 博客里确实有对应课文时，线上模型拿到问题和这些搜索结果，写出回复。它只能用这些结果。回复里还会留下它用过的课文链接。

10. 如果线上模型连不上，助手仍然把搜索结果用普通文字显示出来。它不会编一个答案。外面的说明也一样：模型改写不了时，就在同一个标签下面显示那段公开摘录原文。

## 用的模型

这一版用的是 Cloudflare Workers AI 上的线上模型。网站把问题发给 Cloudflare，Cloudflare 把回复发回来。演示时，笔记本上不需要再跑一个模型。

两个线上模型分工如下：

- 聊天，以及为学习面板阅读课文的那一项工作，都用 Qwen 2.5 Coder 32B。完整名字是 `@cf/qwen/qwen2.5-coder-32b-instruct`。聊天就是读者看到的回复。学习面板那一项是事先跑的，读者打开页面时不会再叫一次模型。
- 按意思搜索用 bge-m3。完整名字是 `@cf/baai/bge-m3`。这个模型不写句子。它把一段文字变成一串数字，这样两段文字才能比较。

上一版是在同一台笔记本上跑更小的模型，程序叫 Ollama：聊天用 Qwen2.5-VL 7B，学习面板用 Qwen2.5 7B，数字串用 nomic-embed-text。这一版不用这些。

## 学习面板是事先准备好的

打开一篇课文时，不会当场让模型决定难度。这些说明已经存在文件 `learning_analysis.json` 里。另外有一条命令，让线上模型把每篇课文读一遍，然后写进这个文件。

只有文件里标明这篇已经准备好，而且概念列表填写正确，面板才会显示。读者这时能看到难度和相关课文的链接。如果检查没通过，或者检查之后课文又被改过，面板会显示“暂不可用”（Unavailable）。发布一篇课文时，旧的说明会被标成过期。这一步不会自己再去叫模型。需要有人重新跑那条命令。

如果某篇还没有任何说明，而它被写在手工整理的文件 `prerequisites_graph.json` 里，面板可以用那份文件。否则就显示暂不可用。第三个文件 `reading_paths.json` 用在读者询问某个主题的阅读路线时。

## 存了什么

数据库里有：

- 课文页面。
- 用来搜索的短段落、每一段对应的数字串，以及这段是不是付费内容。
- 用户、会员、积分，以及每个人打开过哪些课文。
- 聊天记录。每条助手回复可以记下课文链接、跑过哪些搜索，以及还在等确认的那一项改动。
- 阅读清单里的课文。
- 每一次准备好的改动：读者有没有确认，以及最后有没有真正保存。

数据库旁边是上面说的三个文件。它们是事先准备的说明，不是第二个数据库。

## 如果有人问它到底有没有用

9 月 13 日，完整助手和三个更简单的系统回答了同一套 33 道题。那一轮用的是上一版的本地聊天模型。分差来自搜索和工具，这些在现在的线上版本里是一样的。

- 只有模型、看不到任何课文：5/33。
- 只有关键词搜索：7/33。
- 只有按意思搜索：17/33。
- 完整助手，三种搜索都有，再加上其他工具和确认这一步：25/33。

25/33 大约是 76%。我们定的目标是 85%，所以这一轮还没到。同一轮里，只有按意思搜索的那个系统，在 2 道陷阱题上把付费课文正文抄了出来。完整助手没有。

后来又让线上的 Qwen 32B 单独答过同类题目，通过了 26/33。那一次没有带上三个更简单的系统，所以要引用的对比仍然是 25 对 5、7 和 17。

上面的站外查询是这次对比之后才加上的。那一轮的 Helm 题只按“有没有先拒绝”来打分。现在的第一句仍然是拒绝。后面的公开说明标明不是本站课文，所以不计入那次 25/33。
